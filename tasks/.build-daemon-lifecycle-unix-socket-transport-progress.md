### Final-fix review notes

- Node preserves a socket-bearing state record written by Go during startup.
- Node state release uses rename-to-quarantine and no-replace restoration.
- Go state release uses the same ownership quarantine behavior.
- Go backend startup uses an exclusive bind claim and stale-claim quarantine.
- Unix socket stale cleanup quarantines before probing; active listeners are restored and preserved.
- Socket shutdown unlinks before closing, while the bind claim prevents a successor from racing cleanup.

## What the build actually found

Slices 2–4 were already implemented and committed when this run resumed, but none of their
acceptance criteria had tests. Covering them, plus two review rounds and a security audit,
surfaced ten real defects:

**Invariant / correctness**

1. **Mid-boot double-spawn (🔒 INVARIANT 2).** The spawn-lock loser deleted the winner's state file
   on its first unhealthy probe and recursed — a second `saki-backend` on the same port on almost
   every cold start. Fixed in 93048ce; review then found it still live on the *primary* path
   (`reuseRunningDaemon`), fixed in 3d311b4. A booting winner and an OS-recycled PID are
   byte-identical on disk, so state-file **age** is the discriminator.
2. **Cross-daemon state deletion.** `removeDaemonState` had no ownership check and could unlink a
   different daemon's record, orphaning a healthy backend. Now compare-and-delete (`releaseState`).
3. **Per-attempt budget (outcome 5.5).** Three bounded attempts could hang ~33 s against the 10 s
   ceiling. Now one wall-clock deadline across every wait.
4. **`saki backend stop` orphaned a hung daemon.** It decided "is anything running?" from
   `/api/health`, so a live-but-unresponsive daemon was reported "not running" and had its state
   dropped — process alive, nothing tracking it. Liveness decides now.
5. **`stopDaemon` deleted records it didn't own** — a replacement daemon's, or another invocation's
   *held* `pid:-1` spawn lock (which re-opened the double-spawn `O_CREAT|O_EXCL` closes).
6. **Unbounded health probes.** No `AbortSignal`, so a peer that accepts and never answers pinned
   the CLI for undici's ~300 s header timeout — the one case the 10 s ceiling had to cover.
7. **`saki backend status` misreported a manually launched backend** as "not running" (§10 rule 4).

**Security (audit)**

8. **HIGH — state directory trusted on existence.** `mkdir(recursive)` succeeds on a directory
   another user created and never re-applies the mode, and the Node side fell back to a hardcoded
   `/tmp`. On a shared temp root another local user could own `$TMPDIR/saki-<uid>` and control the
   `socketPath` the CLI dials and the PID `stop` signals. Both sides now prove ownership and write
   `O_NOFOLLOW`.
9. **Socket `Host` override never applied.** `Host` is a forbidden header name, so
   `Headers.set('Host', …)` was dropped; OriginGuard accepted socket traffic only because `goUrl`
   happens to be loopback. The adapter rewrites the URL authority instead.
10. **Go state-record clobber.** A second instance on another `PORT` rewrote `goUrl` (redirecting
    every command to itself) and deleted the original's record on exit.

## Not fixed — logged deliberately

- **Local TCP has no authentication** (pre-existing, not introduced here). `OriginGuard` is
  header-based, so it is a CSRF/DNS-rebind control, not authentication: any local user can
  `curl -H 'Host: localhost' … :8788/api/run`. The socket's `0600` is therefore not the effective
  access control while the TCP listener is up. PRD §10 rule 1's "even more local than loopback"
  claim is true in isolation and misleading in composition. Fixing it means socket-only mode or a
  per-daemon token — a scope decision, not a slice.
- **The daemon freezes the first invocation's environment.** `spawnDaemon` passes `...process.env`
  to a detached process that then serves every later command, so an `.env` sourced in one shell
  leaks into agents spawned from another. An allowlist risks breaking real engine spawns; worth its
  own item.

## Manual criterion (not automatable)

- **AC 3.5 [manual]** — Given a run in building state, when `saki backend stop && saki backend start`
  are run, then `saki runs --json` shows the run rehydrated and no data is lost (Rule 7 / Inv-2).
  Requires a real in-flight agent run, so it cannot be asserted in CI. Steps:
  1. `saki run build <roadmap-id>`; wait until `saki runs --json` reports it `building`.
  2. `saki backend stop` → exit 0, `backend stopped`.
  3. `saki backend start` → exit 0, a new PID.
  4. `saki runs --json` → the same runId still listed, journal intact.
  Rehydration itself (`backend/usecase/rehydrate.go`) is covered by the Go suite; what is unverified
  is only that a daemon stop/start cycle triggers it.
